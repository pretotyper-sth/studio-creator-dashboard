## 실측 스냅샷 (`/snapshot/`)

2026-07-31 기준으로 Snowflake `MART_PROD`를 조회해 만든 **정지 화면**입니다(판정 재검토 2026-08-07).
자동 갱신되지 않으며, 갱신하려면 쿼리를 다시 돌려 `snapshot/data.js`를 교체해야 합니다.

### 판정은 두 가지뿐 (2026-08-07 재판정)

이전에는 지표를 세 단계(실측 / 주의 / 불가)로 나누고, 「주의」 칸에 정의를 대체하거나
마트에 없는 인원을 원천에서 세어 더해 만든 값을 실었습니다. 그 방식을 버렸습니다.
지표 40개를 **실측 10개 · 측정 불가 30개** 두 가지로만 판정합니다.

실측이 되려면 아래 세 조건을 모두 만족해야 합니다.

1. 원천이 한 테이블이고, 그 테이블의 로깅이 관측 구간(2026-02~07) 내내 끊기지 않았다
2. 정의를 대체하지 않았고, 마트에 없는 수를 원천에서 세어 더하지 않았다
3. 독립된 다른 원천과 대조했을 때 자릿수 차이가 나지 않는다
4. **「누적」이라 부른다면 시작점이 실제로 서비스 시작이어야 한다**

하나라도 못 지키면 **값을 만들지 않고** 측정 불가로 둡니다(딤드 처리 + ✕ 오버레이).
이전 스냅샷의 보정값 — 첫 편집 809 · 첫 퍼블리시 187 · 90일 퍼블리시 108 · 누적 월드 673 ·
7월 신규 131 — 은 모두 2번을 어긴 값이라 화면에서 내렸습니다. 근거 수치는 지웠다는 사실과
함께 각 블록 툴팁과 `data.js` 주석에 남아 있습니다.

4번 때문에 **누적 지표는 지금 하나도 남지 않았습니다.** 어느 것도 시작점이 서비스 시작이
아닙니다.

| 누적 지표 | 실제 시작점 | 서비스 시작인가 |
| --- | --- | --- |
| 누적 스튜디오 로그인 · 에디터 진입 | 2025-05-01 (`fct_creator_first_login_date`) | ✕ 런칭은 2025년 3월 |
| 누적 첫 퍼블리시 · 퍼블리시 월드 | 2025-08-12 (쿠킹 로그) | ✕ |
| 플레이된 UGC 월드 | 2024-10-15 (플레이 로그) | ✕ |

### 「누적 스튜디오 로그인 2,401」을 내린 이유

시작점이 두 겹으로 어긋납니다.

- 스튜디오 런칭은 **2025년 3월**이고, `studio_log`는 **2025-03-12**, `studio_login` 이벤트는
  **2025-03-26**부터 쌓입니다.
- 그런데 이 값을 만드는 `fct_creator_first_login_date`는 `first_studio_login_date`의 최솟값이
  **2025-05-01**입니다. 런칭 후 **약 7주가 통째로 빠집니다.**

크기도 확인됐습니다. **2026-07-22** 조회에서 원천 `studio_login`의 유니크 계정은 **2,879명**
이었는데, 그보다 **2주 늦은** 기준인 마트 값이 **2,401명**입니다. 누적값은 시간이 지나도
줄어들 수 없으므로 갭은 **최소 478명(16.6%)**이고 실제로는 더 큽니다. 시작점 누락만으로
설명되지 않는 부분이 있어 원인 규명이 필요합니다.

**비율은 살아 있습니다.** 로그인과 에디터 진입은 같은 테이블·같은 모집단이라
**69%**라는 전환율 자체는 성립합니다. 다만 인용할 때
「2025-05-01 이후 첫 로그인이 기록된 계정 중 69%가 에디터에 진입」이라고 모집단을 붙여야 하고,
**인원 수(2,401 → 1,653)는 쓸 수 없습니다.** 화면에서도 비율만 남기고 인원은 뺐습니다.

같은 이유로 이 값을 분모로 쓰던 **편집 전환율**과 **온보딩 퍼널**의 절대 인원도 내렸습니다.

참고로 회원가입 쪽은 반대입니다 — 원천 `WEB_ACCOUNT_CREATE`는 **2024-10-08**부터 3,852건이
정상 적재돼 있습니다. 문제는 적재가 아니라 **식별자 연결**(웹로그에 `user_id`가 안 붙음)입니다.

살아남은 실측 10개는 전부 세 테이블에서 나옵니다.

| 테이블 | 나오는 지표 | 비고 |
| --- | --- | --- |
| `FCT_STUDIO_CREATOR_MASTER` | MAU · 90일 활성 스튜디오 계정 · 주간 신규 · 인/아웃 · 복귀 · 국가 | 단절 없음. 단 «편집»을 세지 못함 (아래 참고) |
| `FCT_WORLD_ANALYTICS` | 플레이된 UGC 월드 수 · 방문 중앙값 · 상위 10% 점유율 | `dau > 0` 필터 필수 |
| `FCT_STUDIO_AGENT_TOKEN_USAGE` | Agent 사용률 | 2026-05-18부터 |

✕ 배지나 블록에 마우스를 올리면 무엇이 한계인지, 어디까지 믿어도 되는지, 대신 무엇을
보면 되는지, 정확히 보려면 어떤 로깅·DW·운영 작업이 필요한지가 나옵니다. 원인이 릴리즈
변경이나 원천 로그까지 추적된 지표에는 `근본 원인 추적` 절이 따로 붙습니다.

### 「활동 · 신규 · 창작」을 각각 무엇으로 세는가

스튜디오 관련 지표는 전부 `studio_log` 한 테이블에서 나옵니다. 이 테이블은 스튜디오에서 일어난
**모든 이벤트**를 한 행씩 담고, 종류는 `event_name`으로 구분됩니다(`studio_login`, `world_create`,
`world_modified`, `studio_asset_click`, `save_attempt`, `publish_result`, `system_logs` 등).
어떤 `event_name`을 조건으로 거느냐에 따라 세 단계가 갈립니다.

| 단계 | 조건 | 쓰는 카드 |
| --- | --- | --- |
| ① 스튜디오 로그인 | **조건 없음** — `accountid`가 비어 있지 않은 이벤트 1건 이상 | MAU · 90일 활성 스튜디오 계정 · 주간 신규 · 국가별 · 인/아웃 · 복귀 · Agent 사용률 분모 |
| ② 에디터 진입 | `event_name = 'world_create'` | 온보딩 퍼널 2번째 칸 (누적 1,653명) |
| ③ 편집 = 「창작」 | `event_name = 'world_modified'` AND `event_value` ∈ 5종 | **없음** — 측정 불가 |

**활동·신규는 둘 다 ①, 즉 스튜디오 로그인 기준입니다.** 화면 문구도 그대로 「스튜디오 로그인
기준」이라고만 씁니다.

- **MAU** = 그 달에 스튜디오를 한 번이라도 켠 계정 수. 켜고 바로 나가도 포함되고 편집·저장·퍼블리시
  여부는 보지 않습니다.
- **주간 신규** = 스튜디오를 **처음 켠 주**(계정별 `MIN(dt)`). **처음 편집한 주가 아닙니다**
  (그건 `first_edit_date`로 별도 컬럼입니다).
- **90일 활성** = 최근 90일 안에 스튜디오를 켠 유니크 계정.

#### ①을 「로그인」이라 불러도 되는지 — 확인 완료

구현상 ①에는 `event_name` 조건이 없어서, 로그인 없이 다른 이벤트만 남은 계정이 섞일 수
있는지가 남은 의문이었습니다. 2026-08-07 조회로 확인했습니다.

```sql
SELECT COUNT(DISTINCT accountid) AS any_event_accts,
       COUNT(DISTINCT CASE WHEN event_name = 'studio_login' THEN accountid END) AS login_accts
FROM PROD.RAW_MERGED.STUDIO_LOG
WHERE dt BETWEEN '2026-08-01' AND '2026-08-07'
  AND accountid IS NOT NULL AND accountid <> '';
```

이벤트를 남긴 계정 **51개** 중 `studio_login`이 있는 계정이 **50개**입니다. 차이 1개는 세션이
주 경계를 넘은 경우로 보이고 월·90일 유니크에서는 흡수됩니다. **로그인 기준으로 읽어도
됩니다**로 결론 내고, 카드 문구를 「스튜디오 로그인 기준」으로 단순화했습니다.

### 「활성 창작 크리에이터」의 기준과, 왜 그 기준으로는 못 세는가

팀 표준 정의는 `fct_creator_first_login_date`가 `first_edit_date`를 만들 때 쓰는 것과 같습니다.

```sql
event_name = 'world_modified'
AND event_value IN ('foundation_design', 'technical_design',
                    'script_generation', 'script_modified', 'object_transform_modified')
```

**대시보드의 로스터는 이 기준을 쓰지 않습니다.** 위 ①입니다. `FCT_STUDIO_CREATOR_MASTER`는
`studio_log`에 `accountid`가 비어 있지 않은 이벤트가 하루 1건이라도 있으면 행을 만들고,
**`event_name` 필터가 전혀 없습니다.**

```sql
-- dbt/snowflake_mart/models/mart/app/fct_studio_creator_master.sql
SELECT DISTINCT dt,
       first_value(country) over(partition by dt, accountid order by ts) as daily_country,
       accountid
FROM {{ ref('studio_log') }}
WHERE NULLIF(TRIM(accountid), '') IS NOT NULL   -- 이게 유일한 조건
```

그래서 `studio_login`(스튜디오를 켜기만 함), `studio_asset_click`(에셋을 눌러봄),
`system_logs`(크래시 로그)까지 편집과 같은 자격으로 들어옵니다. 컬럼도 `dt` · `accountid` ·
`daily_country` · `user_type`(`exist`/`new`) · `surrogate_key` 다섯 개뿐이라 **활동 종류를
사후에 가려낼 방법이 없습니다.**

조치는 두 가지입니다.

1. 이 로스터에서 나오는 지표의 **이름을 실제 세는 것에 맞췄습니다** — 「90일 활성 창작
   크리에이터」 → **「90일 활성 스튜디오 계정」**, 「주간 신규 크리에이터」 →
   **「주간 신규 스튜디오 계정」**, 「국가별 활성 크리에이터」 → **「국가별 활성 스튜디오 계정」**.
   숫자 자체(379명 등)는 세 조건을 다 만족하는 깨끗한 실측이라 그대로 둡니다.
2. 원래 정의의 지표를 **`editCreators90`(90일 활성 창작 크리에이터, 편집 기준)로 신설하고
   측정 불가로 표시**했습니다.

측정 불가인 이유는 정의가 없어서가 아니라 **그레인** 때문입니다. 90일 유니크를 세려면
계정×일자로 편집 여부가 남아 있어야 하는데, 마트에 그 테이블이 없습니다
(`FCT_STUDIO_FUNNEL`은 하루 단위 집계라 계정 목록이 없어 90일 중복 제거가 안 되고,
`event_value` 필터도 없습니다). 원본 로그는 이미 쌓이고 있으므로 **신규 로깅 없이
dbt 모델 하나(`stg_studio_log_daily`, accountid × event_name × 일자)만 추가하면 열립니다.**

차이의 크기는 셀 수 없지만 작지 않을 가능성이 높습니다 — 같은 마트 테이블 안에서 스튜디오
로그인이 기록된 계정 중 첫 편집까지 간 비율이 **31%**(739/2,401)입니다. 두 값 모두 절대
인원으로는 못 쓰지만, 비율만 보면 로그인 계정의 3분의 1 이하만 편집에 도달합니다.

`inout`의 카드 설명이 "최근 90일 안에 한 번이라도 **편집한** 크리에이터 명단"이라고
잘못 쓰여 있던 것도 같이 고쳤습니다. 주간 신규는 7/27~7/31 5일치 부분 주를 차트에서 뺐습니다.

### 「퍼블리시」의 기준 — 세고 있는 것은 «배포»가 아니라 «업로드 시도»

파이프라인 이야기에 앞서 정의부터 어긋나 있습니다. 대시보드가 세는 퍼블리시는
`WORLD_PUBLISH_STARTED`가 찍힌 `(world_id, world_version)`이고, 이 이벤트는
**스튜디오에서 업로드(쿠킹)를 시작한 시점**에 찍힙니다. 성공 여부는
`world_cooking_completed.status`로 판정합니다(`stg_world_cooking.sql`).

제품의 상태값은 네 단계입니다([상태값 문서](https://overdare.atlassian.net/wiki/spaces/NFTMetaverse/pages/28939503)).

| 상태 | 설명 | Home 노출 | 접속 |
| --- | --- | --- | --- |
| Ready for Publishing (Draft) | publish later 선택 · 쿠킹은 완료 | ✕ | QR로만 (모바일 테스트) |
| Publishing | 쿠킹 진행 중 | ✕ | ✕ |
| Published | 배포 완료 | ○ | ○ |
| Unused | 신규 버전에 밀린 이전 버전 | ✕ | ✕ |

**이 상태값은 로그 어디에도 없습니다.** `world_publish_started`·`world_cooking_requested`·
`world_cooking_completed` 세 이벤트 모두 상태 컬럼이 없고, 마트의 `fct_studio_cooking`도
쿠킹 성공/실패만 남깁니다. 결과적으로 세 가지가 섞입니다.

1. **publish later로 쿠킹만 끝낸 월드도 +1** — Ready for Publishing은 문서상 "cooking 완료"
   상태라 쿠킹 로그가 남습니다. 한 번도 Live였던 적 없는 모바일 테스트용 월드가
   「퍼블리시 월드」에 들어가고, publish now와 구분할 필드가 없습니다.
2. **최초 퍼블리시일이 앞당겨짐** — v1~v4를 테스트로 올리고 v5에서 publish now를 하면
   월드 수로는 1개지만 최초 퍼블리시 달은 **v5가 아니라 v1의 달**입니다. TTFP도 같은 방향으로
   짧아집니다.
3. **Unused·Banned가 빠지지 않음** — 누적은 단조 증가만 합니다.

**플래그가 없다는 것은 스키마로 확정했습니다**(2026-08-07 PROD 조회). `WORLD_PUBLISH_STARTED`도
`PLACE_PUBLISH_STARTED`도 컬럼이 `DT · ACCOUNTID · TIMESTAMP · GROUPID · {WORLD|PLACE}ID ·
{WORLD|PLACE}VERSION · PUBLISHSTARTEDAT · NAMESPACE · LOGMETA_LOGID`뿐이고 publish 방식이나
결과 상태를 담은 필드가 없습니다.

**남은 미확정 하나** — publish later 경로가 이 이벤트를 남기는지입니다. 남긴다면 Draft가 섞여
과대집계고, 안 남긴다면 반대로 모바일 테스트를 거쳐 실제 배포한 월드가 통째로 빠집니다.
**보정 방향이 정반대**라 이게 먼저입니다.

그런데 **로그 분석으로는 못 가립니다.** 8/1~8/7 `PLACE_PUBLISH_STARTED`를
`(placeid, placeversion)`으로 묶으면 124개 버전 중 **121개가 정확히 1건**입니다(2건이 2개,
4건이 1개로 재시도로 보입니다). 즉 버전당 이벤트가 한 번만 발생하고, publish later 뒤에
나중에 publish now를 눌러도 두 번째 이벤트가 남지 않습니다. 제품 동작을 물어서 확정하는
수밖에 없어 작업 요청 탭에 **운영 항목**으로 넣었습니다.

### 월별 신규 퍼블리시 월드 (상태별) — 축 두 개가 각각 막혀 있습니다

가상 데이터는 이 카드를 Published / Update Required / 기타로 쌓은 막대로 그립니다.
실측에서는 **막대 높이와 색 구분이 서로 다른 이유로** 못 그립니다. 카드 구조는 가상 데이터와
같게 두고 두 사유를 카드 설명과 ✕ 블록에 나눠 적었습니다.

- **막대 높이(월드 수)** — `world_version`이 5/17 이후 전부 `'1'`이라 신규와 업데이트가
  구분되지 않습니다. 아래 place 이관 절 참고.
- **색 구분(상태)** — 상태값이 로그에 없습니다. 하이커 `world_information_meta`에만 있고
  그마저 최근 30일 활성 월드 162개만 내려옵니다(전체 3,722개 중 4.4%). 활성 월드는 정의상
  Published에 쏠려 있어 부분 집합의 상태 구성은 전체를 대표하지 않습니다.
- **전량 적재가 돼도 월별 분해는 별개** — 메타는 현재 시점 스냅샷이라 상태 변경 이력이
  없습니다. 「그 월드가 퍼블리시된 달의 상태」를 복원할 수 없고, 지금 Update Required인 월드가
  처음부터 그랬는지 나중에 내려간 것인지도 구분되지 않습니다. SCD Type 2로 이력을 남기는
  작업을 별도 항목으로 추가했습니다.

### 퍼블리시 계열이 통째로 죽은 이유 — 5/17 place 이관

개별 버그가 아니라 **제품 구조 변경을 DW가 따라가지 못한 것**입니다. v34.0.0(2026-05-18)
Places & Teleport 도입으로 월드 1개가 「Start Place + 복수 Sub Place」 구조가 됐고, 쿠킹 이벤트
발행 코드가 world 단위에서 place 단위로 옮겨갔습니다.

**2026-08-07 PROD 원천 조회로 확정했습니다.** 이전에는 DEV 관측과 릴리즈 노트로 추정한
내용이었는데, 이제 프로덕션 수치로 확인됩니다.

| 이벤트 (PROD.RAW_MERGED, namespace='live') | 8/1~8/7 |
| --- | --- |
| `WORLD_COOKING_COMPLETED` | **0건** |
| `WORLD_PUBLISH_STARTED` | 12건 / 계정 8 / 월드 12 |
| `PLACE_COOKING_COMPLETED` | 240건 / place 23 |
| `PLACE_PUBLISH_STARTED` | 129건 / 계정 12 / place 23 |

- **place 이벤트의 PROD 최초 적재일은 2026-07-14**입니다(7/13까지 0건). world 완료 로그가
  끊긴 7/10과 사이에 **3~4일 공백**이 있습니다.
- 7/14 이후 두 체계가 **병존**합니다. 7/22 기준 place 65건 vs world 10건이고 일부 날짜는
  world가 0건입니다. 구버전 클라이언트 잔량으로 보이며, **world 이벤트만 보면 대부분을
  놓칩니다.**
- **`MART_PROD`에 이름에 place가 들어간 테이블은 여전히 0개**입니다(같은 날 재확인).
  제품은 7/14에 옮겨갔고 마트는 따라가지 않았습니다.
- 마트에 월드 상태 컬럼도 **없습니다** — `MART_PROD.INFORMATION_SCHEMA`에서 world/meta 계열
  테이블의 status·exposure·access 컬럼을 훑으면 무관한 3건(접속 시각·세션 id)뿐입니다.

바꿔 말하면 **쓸 테이블은 이미 PROD에 다 있습니다.** `PLACE_PUBLISH_STARTED`는
`ACCOUNTID`와 `GROUPID`까지 갖고 있어 크리에이터 귀속도 됩니다. **빠진 것은 `world_id`
하나**이고, 마트가 이 세 테이블을 아직 쓰지 않을 뿐입니다.

재작성 전에 정리할 것이 하나 더 있습니다. `PLACE_COOKING_COMPLETED`의 status는 같은 기간
`'success'` 120건과 `'COOKED'` 120건이 **같은 place 23개에 대해 정확히 1:1로** 들어옵니다.
표기 체계가 둘이라 그대로 세면 두 배가 되고, `'success'`만 거르면 절반을 버립니다.

파생 증상 넷:

1. **성공 판정 붕괴** — `stg_world_cooking`이 `WORLD_PUBLISH_STARTED`에 완료 로그를 조인해
   success를 판정하는데, 완료 로그가 live에 0건이라 전부 failure가 됩니다. CASE문이
   조인 실패(NULL)를 ELSE로 흘려 failure로 확정해 **로그 누락과 제품 실패가 구분되지 않습니다.**
2. **신규/업데이트 구분 붕괴** — `world_version`이 5/17부터 전부 `'1'`입니다(3~5월은 1~340).
3. **`world_id` 연속성 단절** — 이전 2000번대와 이후 3000번대가 **겹침 0**이고 옛↔새 매핑이
   없습니다(서버 확인 완료). 누적이 성립하지 않는 직접적인 이유입니다.
4. **재발행 유실** — 이관 전(3/1~5/16) 월드의 51.5%가 2회 이상 발행이었는데 이관 후 0건입니다.

대체 원천 후보도 각각 못 씁니다. `studio_log`의 `publish_result=success`는 클라이언트가
hub 리다이렉트 순간 무조건 찍어 쿠킹 완료를 보장하지 않고(5/18 이후 578개 vs 실제 place
쿠킹 로그 188개), `WORLD_PUBLISH_STARTED`는 최초 발행만 남으며, `place_cooking_completed`는
가장 정확하지만 **이벤트에 `world_id`가 없어** 월드 단위로 셀 수 없습니다.

### 하이커(운영 어드민) 대조 — 어느 쪽도 정답이 아닙니다

하이커 메타는 `PROD.THIRDPARTY`의 두 테이블로 들어오는데 둘 다 한계가 뚜렷합니다.

- `world_information_meta` — 하루 160여 개만 들어옵니다. 최근 30일 안에 플레이가 있었던
  월드 162개와 정확히 일치하고 경계 2건까지 설명됩니다. 즉 **「최근 30일 활성 월드」**
  목록이지 전량이 아닙니다. 월드 상태 3축(`accessStatus` / `exposureStatus` /
  `currentVersion.status`)이 여기 있어서 **상태는 활성 월드에만 채워집니다.**
- `place_information_meta` — place 3,752개 / 월드 3,722개로 전량에 가깝지만 **2026-07-09부터**이고
  3,536개가 그날 백필로 한꺼번에 들어왔습니다. payload에 `createdAt`이 없어 **월드 생성일과
  7/9 이전 이력을 복원할 수 없습니다.**

그래서 자주 인용되는 네 숫자는 서로 다른 것을 셉니다 — **3,722**(하이커 place 기준 존재하는
월드) / **1,167**(`fct_world_analytics` 등재) / **673**(쿠킹 이력) / **162**(7월에 실제로 플레이됨).
「지금 서비스 중인 월드」에 답하려면 상태 3축이 전량 월드에 채워져야 하는데 지금은 활성
162개에만 있습니다. 이 대시보드는 확실히 셀 수 있는 **162**만 씁니다. 화면에서는
`작업 요청` 탭의 「네 숫자가 서로 다른 것을 셉니다」 카드에 같은 내용이 있습니다.

### `작업 요청` 탭 — 측정 불가를 여는 작업 목록

지표 탭 안에 섞여 있던 「이 화면을 되살리려면」 표와 하이커 대조 카드를 `지표 정의` 뒤
**`작업 요청` 탭**으로 옮겼습니다. 지표를 보는 화면과 고칠 것을 논의하는 화면을 섞지 않기
위해서입니다.

내용은 `snapshot/data.js`의 **`OPS`** 배열이 원본입니다. 7개 묶음 · 작업 34건이고,
각 작업의 `m` 배열이 그 작업으로 되살아나는 지표 키를 가리킵니다. 화면에서 **지표 이름을
누르면 그 지표 카드로 이동**합니다(카드 없이 정의만 있는 지표는 `지표 정의` 탭의 해당 행으로
이동한 뒤 잠깐 강조됩니다).

| 묶음 | 작업 수 | 핵심 |
| --- | --- | --- |
| 퍼블리시 파이프라인 복구 | 9 | 5/17 place 이관 후속 + 퍼블리시 정의 확정. 측정 불가 30개 중 10개가 여기 걸림 |

영향 범위가 가장 큰 두 건은 이렇습니다.

- **place 쿠킹 이벤트에 `world_id` 기록** (또는 place↔world 매핑 확정) — 지표 8개가 걸려

검사합니다. 지표를 늘리고 `OPS`를 안 늘리면 감사에서 실패하므로 목록이 낡을 수 없습니다.

### 카드에 담는 것과 담지 않는 것

**카드 본문은 지표의 정의와 숫자만** 싣습니다. 한계·근거·필요 작업은 툴팁으로 내리고,
"그래서 무슨 일이 벌어진 것인가"라는 결론은 대시보드에 넣지 않습니다. 보는 기간을 바꾸면
답이 달라지는데 결론 문장은 고정돼 있어서, 읽는 사람이 숫자를 스스로 해석할 길을 막습니다.

특정 시점을 하드코딩한 일회성 분석도 카드로 만들지 않습니다. 기간 필터를 따르지 않아
필터를 움직여도 값이 그대로 남고, 그게 지표인지 그때의 답인지 구분이 안 됩니다. 그런
분석의 근거 수치는 관련 지표의 툴팁에 두고, 결론은 별도 리포트로 전달합니다.

"상위 10% 월드의 방문 점유율" 카드에는 구성 월드 17개를 월드명 × 점유율로 보여주는
목록 툴팁이 붙어 있습니다.

### 기간 필터

상단 기간(최근 6/3/1개월)은 월 시리즈(2026-02~07)를 뒤에서 N개월 잘라 적용합니다.

- **합산 가능** — 방문 건수, 신규 퍼블리시 월드, 복귀 크리에이터, 진입/이탈, Agent 세션은
  선택 창의 합계로 바뀝니다.
- **합산 불가** — MAU나 "한 번이라도 플레이된 월드 수"는 각 달의 유니크라 여러 달을 더할 수 없어
  대표값은 항상 최근 달(7월)이고, 창에 대해서는 월평균·월최대만 보여줍니다.
- **기간 무관** — 90일 슬라이딩(활성·퍼블리시 전환·Agent 사용률), 누적 퍼널, 코호트,
  국가 구성은 정의 자체가 고정 창이라 값이 바뀌지 않으며 `기간 무관` 배지가 붙습니다.

1개월을 고르면 월 포인트가 하나뿐이라 추세 꺾은선이 단일 막대로 바뀝니다. 주·일 단위
분해는 현재 마트에 없어 지원하지 않습니다(주간 신규 크리에이터만 7월 4개 주차로 좁혀짐).

### 알려진 정의 이슈

- **Live 월드**: `fct_world_analytics`의 `namespace`는 전 구간 `'live'` 단일값이라 필터가 되지
  않고, 이 테이블은 방문이 0인 날에도 행을 남깁니다. 따라서 "행이 있는 월드 수"는 누적 등재
  수이지 서비스 중인 월드가 아닙니다. 비율 지표를 내리고 한 번이라도 플레이된 월드의 절대 수로 대체했습니다.
- **회원가입 단계**: 웹로그 `user_id` 커버리지 부족(62.6%)으로 퍼널에서 제외. 스튜디오 로그인을
  100% 기준선으로 사용합니다.
- **퍼블리시 성공 판정**: 위 「5/17 place 이관」 절 참고. 지표를 만들지 않고 측정 불가로 둡니다.
- **첫 퍼블리시 인원**: 마트 기록 149명 / 원천에서 누락 38명(7/10~7/31 첫 퍼블리시, 전원
  라이브 월드 보유 확인, 전원 2026년 6~7월 스튜디오 첫 로그인)을 더하면 187명. **어느 쪽도
  쓰지 않습니다** — 187은 확인된 누락만 더한 하한이고, 쿠킹 로그가 2025-08부터라 그 이전
  퍼블리시자는 어느 쪽에도 없습니다(2025-08 이전에 이미 방문되던 월드가 544개).
- **첫 편집 인원**: `world_modified` 편집 이벤트가 원천에 있는데 `first_edit_date`가 NULL인
  계정이 7/01~7/31에 **70명**입니다(4월·6월 초 동일 조회는 0건 — 7월에 생긴 회귀). 5일 연속
  편집 이벤트가 있는데도 NULL인 계정이 있어 지연 적재로 설명되지 않습니다. 마트 기록 739 /
  누락을 더하면 809인데, 차이가 전부 7월에서 나와 **이 지표로는 7월 온보딩을 판단할 수
  없습니다.** 둘 다 화면에 싣지 않습니다.
- **활동 시간**: `FCT_STUDIO_TS.USER_TOTAL_TS`는 세션 종료 누락 시 자정까지 계상하고,
  `studio_version` 공백 행과 실제 버전 행으로 쪼개져 같은 시간을 중복 계상합니다. 1인당 하루
  19.7~27.3시간이 나와 지표로 쓸 수 없어 **활동 일수**로 대체했습니다.
- **TTFP 기준선**: 게임 가입일 대신 **스튜디오 첫 로그인일**이 맞습니다(4월 296일 → 7일). 다만
  기준선을 바로잡아도 분자인 첫 퍼블리시일이 5/17 이후 안 찍혀 측정 불가입니다. 7월 표본
  18명은 실제 56명의 3분의 1이고, 빠진 쪽이 「들어오자마자 낸」 계정이라 중앙값이 길게 나옵니다.
- **업데이트(v2+) 단계**: `first_update_date`가 2026-05-15 이후 적재되지 않아 퍼널에서 제외했고,
  이에 의존하는 지속 작업률도 불가로 내렸습니다.

### 가상 데이터의 내부 정합성

2026-08-04에 실측 검증과 같은 기준으로 `data.js`도 전수 점검해 재정합했습니다. 세그먼트
(Independent / Partner / 내부)를 진실로 두고 전체 값을 다시 계산했으며, 티어 포함관계·퍼널
단조성·파생 비율·`utmShare` 합 = 누적 가입까지 교차검증합니다. 점검 스크립트는
`.audit-mock.cjs`(가상)와 `.audit-snap.cjs`(실측)이고, `.check-both.cjs`는 두 페이지를
헤드리스로 띄워 빈 차트·`NaN` 누출·배지↔레지스트리 짝을 확인합니다.

## 구조

- 데이터: `data.js`로 분리 — 갱신 시 이 파일만 교체
- 차트: 의존성 없는 네이티브 SVG (`index.html` 인라인 스크립트)
- 월 추이 차트의 마지막 포인트(부분 집계)는 점선/반투명 표시

### 2열 카드 정렬

`.row2`에 나란히 놓인 두 카드는 설명 줄 수와 스탯 한 줄의 유무가 서로
달라서 그냥 두면 차트가 어긋난 높이에서 시작합니다. 세 가지로 맞춥니다.

  차트가 밀려서, 한쪽에만 배너가 있는 쌍이 반드시 어긋납니다.
- `alignRowBodies()`가 쌍마다 설명(`.cap`) 높이를 큰 쪽으로 통일합니다(`--caph`).
- 그래도 남는 차이(한쪽에만 있는 스탯 줄 등)는 차트 위 여백으로 흡수해 **차트 시작 높이를
  일치**시킵니다. 폭에 따라 줄바꿈이 달라지므로 리사이즈·탭 전환마다 다시 계산합니다.

두 페이지의 같은 지표 카드는 제목·설명 문장 구조도 같게 유지합니다. `.rows.cjs`가 모든 탭을
돌며 2열 쌍의 본문·차트 시작 높이가 어긋나는 곳을 잡아냅니다.

### 설명 복사

한계 설명을 그대로 긁어 질문·문서에 붙이는 일이 많아 세 가지를 보장합니다.

- **툴팁이 설명 박스를 가리지 않습니다.** 아래 → 위 → 오른쪽 → 왼쪽 순으로 자리를 찾고,
  들어갈 곳이 여럿이면 다른 카드 설명을 덜 가리는 쪽을 고릅니다. 예전에는 위아래가 모두
  부족하면 화면 위쪽에 그대로 붙어 정작 읽으려던 글자를 덮었습니다.
- **배지를 클릭하면 툴팁이 고정**돼(테두리가 밝아집니다) 마우스를 떼도 닫히지 않습니다.
  드래그로 긁는 중에는 밖으로 나가도 유지되고, `Esc`·닫기 버튼·바깥 클릭으로 풉니다.
- **`설명 복사` 버튼**이 ✕ 측정 불가 마스크와 툴팁 머리글에 있습니다. 화면의
  HTML이 아니라 `AVAIL`·`DETAIL`에서 평문을 다시 만들어 카드 설명·한계·믿을 수 있는 범위·
  오해·대안·필요한 작업·소스를 한 덩어리로 복사합니다. 목록형 툴팁(상위 10% 월드)은 탭으로
  구분한 표라 시트에 바로 붙습니다.

동작 점검은 `.copy.cjs`(겹침·선택·복사 내용)와 `.copy2.cjs`(실제 드래그·표 복사·좁은 화면)
입니다. 페이지가 빽빽하면 큰 툴팁이 *다른* 카드의 설명과 겹치는 것은 피할 수 없지만,
**자기 앵커 박스는 어떤 화면 크기에서도 가리지 않습니다**.

## 배포

**`main`에 푸시하면 끝입니다.** `.github/workflows/deploy.yml`이 Cloudflare Pages로 올리고
30초쯤 뒤에 `studio-creator-dashboard.pages.dev`에 반영됩니다. 빌드 도구는 없고
`index.html`·`data.js`·`snapshot/`을 그대로 복사해 올리므로 소스가 곧 배포물입니다.

```bash
git add -A && git commit -m "..." && git push origin main
```

푸시 전에 `node .audit-snap.cjs`가 CI에서 먼저 돌아 **실패하면 배포가 멈춥니다.** `na` 지표에
값이 남아 있거나 작업 요청 탭이 `na` 지표를 빠뜨리면 여기서 걸립니다 — 모순된 수치가 라이브로
새는 것을 막는 장치이니 통과할 때까지 데이터를 고쳐야 합니다.

정적 파일뿐이라 백엔드가 없고, 사내망 없이 열립니다.

### 배포 대상을 Cloudflare 하나로 두는 이유

**도메인이 하나여야 합니다.** 같은 화면이 두 도메인에 뜨면 한쪽이 조용히 낡아 잘못된 수치를
보여줍니다 — 실제로 2026-08-07에 `pages.dev`가 8/4 빌드에 멈춰 있었습니다. `pages.dev`가
공유된 주소이므로 이쪽을 정본으로 두고 GitHub Pages는 껐습니다.

수동 `wrangler` 실행은 OAuth 토큰이 3일 만에 만료되고 사내 TLS 프록시(`CN=*.krafton.com`)
때문에 `NODE_EXTRA_CA_CERTS`를 걸어야 하는데, **CI에서는 둘 다 해당되지 않습니다.** API
토큰은 만료되지 않고 GitHub 러너는 프록시를 타지 않습니다.

### 필요한 시크릿

| 시크릿 | 상태 | 발급 방법 |
| --- | --- | --- |
| `CLOUDFLARE_ACCOUNT_ID` | 설정됨 | `wrangler whoami` |
| `CLOUDFLARE_API_TOKEN` | **직접 넣어야 함** | Cloudflare 대시보드 → My Profile → API Tokens → Create Token → Custom token → 권한 `Account · Cloudflare Pages · Edit` 하나만 |

```bash
gh secret set CLOUDFLARE_API_TOKEN   # 프롬프트에 토큰 붙여넣기
```

토큰이 없으면 워크플로가 첫 단계에서 어떤 시크릿이 없는지 알려주고 멈춥니다. 로컬에서
긴급 배포가 필요하면:

```bash
security find-certificate -a -p /Library/Keychains/System.keychain > /tmp/ca.pem
security find-certificate -a -p /System/Library/Keychains/SystemRootCertificates.keychain >> /tmp/ca.pem
rm -rf dist && mkdir -p dist/snapshot
cp index.html data.js dist/ && cp snapshot/index.html snapshot/data.js dist/snapshot/
NODE_EXTRA_CA_CERTS=/tmp/ca.pem npx wrangler pages deploy dist \
  --project-name=studio-creator-dashboard --branch=main
```
